# 会話するだけで続く自動記憶

2026-11-13 のユーザー指定：普段は会話するだけでよく、手動で記憶に登録する操作は必要ない。

## 実装する流れ

1. 会話の原文を端末に保存する。
2. AIの返答が確定した後、未整理の会話から出来事・好み・約束・関係の変化を抽出する。
3. 発言元と時点を紐づけ、既存の記憶との重複・変更・矛盾を確認して保存する。
4. 次の会話では、現在の話題に関係する記憶を自動で取り出す。

通常の抽出・保存に確認ボタンや承認画面は挟まない。利用者が気になった時だけ
記憶を確認・訂正できる。手動固定の操作は設けない。嘘・推測・創作中の設定を、現実の確定事実と混ぜない。
好みが変化した場合は過去の出来事を消さず、現在の情報と変更時点を記録する。

抽出の失敗や通信切断で会話原文を失わない。未整理の会話は後から再処理でき、
同じ会話を再処理しても二重登録しない。再生成で捨てた返答は記憶の根拠にしない。
記憶抽出もサブスク利用枠を消費するため、未変更部分を毎回読み直す処理は避ける。

## 現在の実装状態（0.2.0）

SQLiteへの追加保存、旧JSONの一度限りの移行、80件ページ表示、出典付きの型付き記憶、
更新履歴、取り消し可能な約束の状態、差分整理ジョブ、索引検索、関連原文の取得を実装した。
事実・出来事・約束は明示された情報に限定し、推測は解釈として区別する。
異なる人物・キー・種類・世界の記憶を置き換える処理は拒否する。

モデルへの現在の発言は全文を渡し、古い文脈と整理バッチはサイズ制限付きで処理する。
長文の一部しか渡せていない場合はtruncatedを明示する。全文はDBへ保全する。
検索はFTS5の日本語文字索引と構造化検索で、埋め込み検索やグラフDBは未導入。

ChatGPTの認証と実際の応答・記憶整理を接続した。アプリへ戻ってからトークン交換を
完了する。応答はSSEまたは完了状態のJSONを検証して確定し、途中の返答は原文にしない。

手動固定・全文一覧・全文コピーは設けない。過去の旧固定記録は互換データとして保全し、
通常の自動抽出とは区別して表示する。AIの意味解釈・矛盾判定の完全性は保証しない。
長期間の日本語会話、暗黙の想起、人物像の維持、過剰な記憶利用は今後の実会話評価が必要。

## 人物自身の緩やかな変化

出来事の記憶とは別に、会話する人物自身の好み・相手との関係・考え方・話し方・気質を
出典付きの現在の人物像として保持する。ユーザーのプロフィールを人物にコピーする処理にはしない。
現在の人物像は検索した記憶の最大12件とは別枠で毎回の返答と記憶抽出へ渡し、
引き継ぎプロフィールと衝突するときは対応する項目だけを優先する。名前や経歴、未更新の設定は保つ。

返答を保存し、通常の記憶を最大3バッチ整理した後、人物像の振り返りを最大1回行う。
通常の記憶ジョブがないときも振り返りは再試行できる。原文は古い発言を含めて範囲とサイズを制限し、
切り詰めた発言にはtruncatedを付ける。モデルへ渡した原文のIDだけを更新の根拠に認める。

12件以上の新しい発言で振り返りを予定し、1回で進める範囲は最大24件とする。
好みと関係はuser・assistantそれぞれ2件以上の根拠が必要で、考え方・話し方・気質は
それぞれ6件以上、発言IDで24以上の幅と前回変更から24以上の間隔を必要とする。
どの変更にも前回の振り返り後のuser・assistantの根拠を最低1件ずつ含める。
一時的な気分、ロールプレイ、その場だけの命令や自己紹介の反復を恒久的な変化にはしない。

変更なしも正常な結果として振り返り済みの位置を進める。更新・通信が失敗した場合や中断時は
人物像を確定せず、保存済みの会話と返答を残したまま後から再試行する。
モデルの解釈や実際の話し方への反映は、自動テストに加えて実会話での評価が必要。

DBはschema 3へトランザクション内で移行し、schema 1/2の会話・出典・人物資料を保つ。
人物像の変更と変更なしのチェックポイントも、Gitの差分履歴とZIPのスナップショットへ含める。
schema 3に対応しない旧CoreはDBを開かず、人物像を無視した書き出しを防ぐ。
回数・間隔は会話数による初期の目安で、独立した経験や自然な成長を機械的に証明するものではない。
現在像の生成は変更履歴を読むため、大量履歴での実機負荷は別途測り、必要なら現在値を実体化する。

## 返答と同時に更新する気持ち

感情・理由・状況は `ChatSession.reply` の返答生成と同じ通信で生成する。通常の返答本文の後に `<assistant_state>` とJSON（`emotion`・`reason`・`event`・`scope`、または `null`）を付け、区切りが分割された生成途中も含めて内部データを画面へ出さない。現在の気持ちがなければ `null` で明示的に解除する。scopeは会話内のsharedか創作内のfictionとし、各文章はUTF-8で768バイト以下にする。

本文と気持ちは `conversation_add_reply` の単一トランザクションで保存する。気持ちはschema 5の追記専用 `assistant_states` に記録し、出典は保存処理が今回のユーザー発言と返答のIDを付ける。通信中断・付属データの形式不備・保存失敗では本文と気持ちを確定せず、保存済みのユーザー原文は残す。区切りのない通常応答や画像だけの応答は本文だけを保存し、以前の気持ちを保つ。切れた区切りも本文へ出さない。気持ちを補うための追加通信は行わない。

整理済みの現在地は従来の12KiB上限を保ち、返答時の気持ちは別枠でJSON全体を12KiB以下に制限する。返答へ渡すcontinuityは両者を合成するため、この気持ちの分だけ上限が増える。

長期記憶と話題・体験の整理は引き続き裏で行い、現在の気持ちを再生成しない。返答用のcontinuityとアイコン表示は `assistant_states` の最新値を優先し、古い記憶整理の完了で巻き戻さない。`assistant_state_through_id` は気持ちを保存した返答IDを表し、話題・体験の整理済み位置 `through_id` とは分ける。新しい返答の記録がまだない場合は、旧 `continuity_revisions` の気持ちを読み出す。schema 1〜4の原文と記憶を保ったまま5へ移行し、新しい気持ちの履歴もGit差分とZIPへ含める。

## 0.5.0：会話の現在地と体験

既存の抽出結果 `memories` に `continuity` を加え、同じ通信で更新する。最大6件の話題には候補・順番・決定・保留を、最大6件の体験には出来事・明示された感情・場面・現実と創作の区別を保持する。各項目に根拠の発言IDを1〜8件付け、現在地全体はJSON化後12KiBに制限する。感情と場面の不明部分は空文字とし、推測の感情は既存のinterpretation/inferredへ分ける。保持枠から外れる長期の出来事は、既存のevent記憶にも残す。

現在地の改訂は `continuity_revisions` に追記する。記憶・現在地・ジョブの処理済み位置を同じトランザクションで確定し、検証失敗時はまとめて取り消す。根拠IDはジョブの発言と直前12発言、または前回の現在地が保持する出典に限定する。抽出に渡す補助原文はジョブの終端以降を除外する。従来形式の抽出結果も受け入れ、その場合は現在地を消さない。

返答へは最新の現在地とthrough_idを毎回渡す。現在地の根拠と検索した記憶の根拠、その前後1発言を、直近12発言とは別の予算で取得する。原文は最大2048文字の抜粋であり、長文の省略を明示する。直近原文18,000バイト・追加根拠20,000バイト・検索記憶10,000バイト・現在地12KiBを上限にする。人物プロフィールと人物像は別枠、今回のユーザー入力は従来どおり全文を渡す。原文全体はDBに残る。

現在地より新しい発言の訂正・決定を優先し、過去の感情を現在の気持ちや恒久的な人物像と同一視しない。保存時の検証は形式・出典範囲・上限を確認するもので、モデルの感情解釈が正しいことを証明するものではない。

## 0.5.1：返答と記憶整理の並行処理

返答の完了と保存までが送信待ちの対象である。`ChatSession.reply` は記憶整理を実行せず戻り、UIは送信を再開する。記憶整理は別の `ChatSession` と `MemoryWorker` で進める。整理要求が重なると、実行中の1件と次の1件にまとめる。未処理ジョブはDBから取得するため、要求をまとめても保存済みの会話範囲は失わない。

返答と整理のHTTP要求は同時に実行できる。OAuthの取得・更新は共通ロックで直列化し、古いトークンへの401で更新済みトークンを消さない。停止は返答の通信だけを対象にし、ログアウトとActivity破棄は全通信を停止する。ログアウトのロック取得前後で通信を停止し、認証更新待ちの間に始まった要求も残さない。DB操作は従来のstoreGateとネイティブのmutexで直列化する。人物の変更・追加・削除は、返答と整理の両方が終わるまで待つ。

アプリのプロセス終了後までの継続実行は保証しない。中断した整理ジョブはDBに残り、後続の会話やメニューの再試行で再開する。OSによる通信制限とサーバー側の利用枠・同時実行上限は別に適用される。

返答モデルへの発言本文には内部ラベルを付けない。ID・記録時刻・省略フラグは参照用データのhistoryに置き、input_indexで会話本文に対応付ける。受信時は最終返答以外の明示されたチャネルを除外する。返答に内部ラベルや制御記号、報告された無関係な先頭行が混ざった場合は、途中表示・保存前・既存履歴の表示で取り除く。通常の多言語の引用や日付は維持する。この整理で過去のDB原文を書き換えたり、私的な本文を診断ログへ出したりはしない。

## 0.5.2：AI側の現在の感情

`continuity.assistant_state` に応答する人物自身の現在の感情（emotion）、由来（reason）、きっかけの出来事（event）、現実／創作／共有体験の区別（scope）、根拠発言（source_ids）を保持する。三つの本文は各UTF-8で768バイト以下、根拠は重複なし1〜8件とし、現在地全体の12KiB上限にも含める。ユーザーの感情や恒久的な人物像とは分け、会話に基づく人物の受け止めとして扱う。言葉にされていない内面状態も会話の根拠から整理できるが、未発言の出来事やAIの身体的体験は作らない。

返答には毎回渡し、根拠の原文は直近12発言から外れても追加の原文予算内で取得する。新しい発言を優先し、気持ちの解消や変化を返答に反映する。既存の記憶整理で返答後に更新するため、新しい整理が終わる前の次の返答では、直前の保存済み状態と新しい会話を併用する。気持ちを毎回説明する指示にはしない。

整理結果のassistant_stateがnullなら現在の感情を解除し、省略した旧形式なら前回の状態を保つ。引き継ぎ後の合計サイズ・形式・根拠を検証し、失敗時は前の状態と未処理ジョブを残す。従来のthreads・episodesのみのデータも読み込め、schema 4の既存の改訂・Git差分・ZIPを再利用する。古いCoreは追加項目のあるアーカイブを検証できないため、新しい感情状態を保存した後の旧版への復元には対応しない。

## 0.5.3：チャットでの気持ち表示

AIの吹き出し左の人物アイコンに、最新のAI発言だけ現在のemotionを添える。理由・出来事・出典IDは画面に出さず、過去の発言に現在の気持ちを繰り返し表示しない。整理モデルには短い感情語を求め、長い表示は最大3行で省略する。未整理・nullなら気持ちの代替文を作らない。表示の取得は最新の改訂からemotionだけを読むため、RAG検索は実行しない。バックグラウンド整理の成功時と部分的な保存後の失敗時の両方で表示を読み直す。ストリーミング中はその発言のアイコンに直前の保存済みの気持ちを添える。

同版で短期記憶を過去30往復＋今回の入力（最大61発言）に拡大した。直近原文のJSON化後予算は768KiBにし、各発言最大2048文字の抜粋をJSONのエスケープが多い場合も61件保持できる。今回のユーザー入力は送信時に全文へ戻す。追加根拠20,000バイト・検索記憶10,000バイト・現在地12KiBの別枠は維持する。抽出ジョブの補助原文の検証範囲は引き続きジョブ直前12発言と前回の現在地の出典であり、返答用の履歴を増やしても抽出の出典範囲は拡げない。

## 0.6.0：端末内の意味検索

USearch 2.26.2のHNSW索引と、既存のSQLite FTS・構造化検索を組み合わせる。SQLiteの記憶と出典が原本であり、USearchが返したIDだけで記憶本文を作らない。Coreは最大48件の候補IDの型・範囲・重複を検証し、現行の記憶に結合する。字句検索と意味検索の順位をRRF（定数60）で統合した後、従来どおり最大12記憶と根拠原文を既存のサイズ上限内で取得する。過去の版の明示的な検索は従来の字句検索で扱う。

埋め込みは[Ruri v3 30m](https://huggingface.co/cl-nagoya/ruri-v3-30m)の[固定したONNX量子化版](https://huggingface.co/onnx-community/ruri-v3-30m-ONNX/tree/1b41a27f31213fc55a9c4653c067770e39406408)をONNX Runtime 1.23.2のCPUで実行する。入力はSentencePiece 0.2.1で処理し、元のLlamaTokenizerの非legacy設定と同じくdummy prefixを付けず、先頭・末尾トークンを含め最大256トークンとする。検索には「検索クエリ: 」、記憶には「検索文書: 」の接頭辞を付ける。出力は256次元でmean poolingとL2正規化を行い、USearch内ではf16で保持する。CPU推論は2スレッド、索引の操作は直列化する。近傍24件のうちcosine distance 0.35以下を候補として渡す。距離のしきい値は意味的な正しさを保証しない。

モデルは全人物で共有するアプリ内ディレクトリに初回ダウンロードする。ONNXは37,048,575バイト（SHA256 `bd07545fa4eb8e7765939536944da1138a7e61441d81633adfa1faf218df6bb1`）、トークナイザーは1,831,879バイト（SHA256 `008293028e1a9d9a1038d9b63d989a2319797dfeaa03f171093a57b33a3a8277`）。サイズとSHA256を照合してから原子的に置換する。ダウンロード要求に会話本文は含めず、推論・検索も端末内で行う。初回以外の検索はモデル配布元へ通信しない。

各人物の `.semantic-cache.sqlite3` は、記憶IDごとのベクトルと処理済み位置・モデル版を持つ再生成可能なキャッシュである。Coreから最大16記憶ずつ取得して背景処理し、ベクトルと処理位置を同じキャッシュDBのトランザクションで保存する。上書きされた旧記憶のベクトルは取り除く。再起動時はキャッシュからUSearchを再構築し、破損・モデル版の不一致時はキャッシュだけを再作成する。人物を切り替えた後のCoreを古い背景処理が読み出さないよう、人物IDとActivity状態を確認する。キャッシュはGit・ZIPの原本アーカイブへ含めず、復元後は保存済みの記憶から再生成する。

返答の取得だけを意味検索へ接続し、記憶抽出の文脈・出典範囲は拡げない。索引が未準備の場合は待たずに従来の検索で返答する。失敗時も原文・記憶を保持し、後続の整理や起動時に再試行する。検索は日本語に最適化したモデルの解釈に依存し、長い記憶の後半、代名詞だけの質問、多言語の想起品質は継続評価が必要である。
