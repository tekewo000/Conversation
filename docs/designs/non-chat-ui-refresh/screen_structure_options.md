# 画面構成の比較：チャット以外の刷新

* **対象：** [設計書](./design_draft.md)の画面構成と主要な遷移。
* **状態：** 2026-11-15、ユーザーが案Aを選定。技術設計の承認は別途確認する。
* **前提：** この会話のユーザー指定を引き継ぐ。チャットの見た目と日常操作を保ち、人物、記憶、設定、バックアップの管理画面を刷新する。
* **既存の修正案：** [goldfish_review_report.md](./goldfish_review_report.md)は未承認・未適用のまま。今回の構成選択だけで、その修正案まで一括承認したとは扱わない。

## 比較の前提

メニューを開く既存の操作と、人物アイコンから記憶へ入る既存の操作は残す。チャットにタブや新しい固定ボタンは追加しない。

現在の「短期記憶」は直近の会話原文、「中期記憶」は会話を整理した体験の一覧とその階層を表示する。どの案も現在ある情報の閲覧と整理を扱い、新たな記憶編集、検索、グラフ表示は追加しない。

ChatGPT接続、モデル・Effort・Fast、利用状況、画像生成API、表示設定はアプリ全体に関わる設定として扱う。記憶、人物アイコン、Git保存、ZIP書き出しでは、操作対象の人物を明示する。人物を切り替える操作と、単に管理画面を開く操作を混同しない。

これらは構成を比較するための条件であり、画面の配色、文字、余白や、具体的な状態管理の実装を決めるものではない。

## 案A：目的ごとの管理一覧から進む

### 仕組み

既存メニューの先を管理の一覧画面にする。「人物」「記憶」「設定」「バックアップ」を同じ入口から選べるようにする。一覧には現在の人物と、接続・記憶整理・保存の要点を表示し、それぞれの操作は担当画面へ進める。

```text
チャット → 管理一覧
           ├ 人物 → 切り替え・追加・読み込み・アイコン・削除
           ├ 記憶 → 現在の状態・短期記憶・体験・整理状況
           │         └ 体験の一覧 → 日・場面・出来事の詳細
           ├ 設定 → ChatGPT・応答設定・画像生成API・表示
           └ バックアップ → 現在の人物の保存状態・Git設定・ZIP
```

記憶の長文や体験階層は専用画面で読み、戻ると一つ前の一覧へ戻る。人物アイコンからは同じ記憶画面へ直接入る。設定値の短い選択や確認は、その場から開く小さな画面として扱う。

### 利点と負担

何をしたいかから入口を選べ、設定と記憶の担当を分けやすい。反面、人物のアイコンを変えた後にバックアップするなど、別の分類を続けて操作すると、管理一覧への往復が増える。

### 不向きになる条件

同じ人物について、外見・記憶・保存を頻繁に行き来する使い方。人物ごとの操作対象を各画面で示さないと、どの人物を操作しているか見失いやすい。

## 案B：現在の人物を中心にまとめる

### 仕組み

既存メニューの先を、現在の人物の管理画面にする。その人物の「記憶」「アイコン」「バックアップ」をまとめ、人物の切り替え・追加・読み込みへ進む入口を置く。アプリ共通の設定は別の入口に分ける。

```text
チャット → 現在の人物の管理
           ├ 記憶 → 現在の状態・短期記憶・体験・整理状況
           │         └ 体験の一覧 → 日・場面・出来事の詳細
           ├ アイコン
           ├ バックアップ → 保存状態・Git設定・ZIP
           ├ 人物一覧 → 切り替え・追加・読み込み・削除
           └ アプリ設定 → ChatGPT・応答設定・画像生成API・表示
```

人物に関係する詳細は、その人物の名前を持つ画面として開く。人物アイコンからは記憶へ直接進み、戻る操作でチャットに戻る。人物がまだない場合にも、作成・読み込みと共通設定へ進める入口を表示する。

### 利点と負担

記憶と保存が誰のものかを把握しやすく、一人を継続して使う場面では管理項目をまとめられる。反面、モデルや表示など、人物に依存しない設定の存在が目立ちにくくなる。人物がいない初回の画面も別途扱う必要がある。

### 不向きになる条件

共通設定を頻繁に変える使い方、または人物を多く切り替える使い方。共通設定の入口を人物設定の一部のように見せると、変更が人物だけに適用されるという誤解を生む。

## 案C：管理画面の中だけでタブを切り替える

### 仕組み

既存メニューから、管理用の画面を開く。その画面内に「人物」「記憶」「設定」「保存」のタブを置く。チャットにはタブを追加しない。管理内で分類を直接切り替え、長文や体験の詳細はタブの配下に開く。

```text
チャット → 管理画面［人物 | 記憶 | 設定 | 保存］
                       各分類を管理内で直接切り替え
                       記憶 → 体験の一覧 → 詳細
                       設定 → 接続・応答・画像生成API・表示
```

人物アイコンから入った場合は記憶タブを開く。分類を切り替えた後にどの一覧位置へ戻るか、端末の戻る操作が詳細・管理・チャットのどこへ戻すかを定める必要がある。秘密入力と確定操作を伴う処理は、分類を切り替えても意図せず保存・実行されないようにする。

### 利点と負担

管理中の分類の切り替えに、入口の一覧への往復が要らない。反面、各タブの選択・スクロール・詳細の位置と、戻る順序を整える状態管理が増える。小さい幅や大きな文字でタブ名が収まるかも確認が必要になる。

### 不向きになる条件

管理を開く頻度が低く、毎回一つの操作だけ行う使い方。タブごとの位置を保持する方針が曖昧なままだと、前の人物の情報や古い詳細を表示する問題につながる。

## 比較表

以下は方式上の違いであり、端末や利用者による実測結果ではない。

| 観点 | 案A：目的ごとの一覧 | 案B：人物が中心 | 案C：管理内タブ |
|---|---|---|---|
| 管理を開いた直後 | 目的の一覧 | 現在の人物とその管理 | 選択中の分類の内容 |
| 記憶と保存の関係 | 別の分類、同じ対象人物を表示 | 同じ人物の管理から進む | 分類を直接切り替える |
| 共通設定 | 人物管理と並ぶ分類 | 人物管理から共通設定へ進む | 設定タブ |
| 分類を続けて操作 | 管理一覧へ戻って選ぶ | 人物管理へ戻って選ぶ | タブを選ぶ |
| 長い記憶の閲覧 | 分類から専用画面へ | 人物から専用画面へ | 記憶タブの詳細へ |
| 主な負担 | 分類間の往復 | 共通設定の意味と初回表示 | タブの状態保持と戻る順序 |

## 選定後に書く技術設計

選んだ構成に沿って、各画面の責務、情報の並び、長文の表示と戻る操作、空・読み込み・処理中・失敗の状態を設計書に記載する。

`MainActivity`が行う保存・認証・通信と、`ComposeUi`が行う描画・入力の現行の分担を確認し、今回必要な変更と再利用する部分を具体化する。既存の共通パネルへ固定することも、新しい状態管理基盤を追加することも、今回の構成選択だけで決めない。

構成を選んだ後も、別途の確認を経ずに技術設計の承認、未承認の文章修正の適用、製品コードの実装へ進まない。
