## 実行する確認

1. 初期の全体レビュー：目的、単純さ、既存実装の再利用、矛盾や不要な妥協を確認する。
2. 理解度レビュー：設計書だけを読み、提案と現状を説明できるか確認する。この担当には上記の参考ファイルを渡さない。
3. 設計・構成・文章レビュー：機能仕様の基準と照らし合わせる。
4. 中間の全体レビュー：それまでの報告を踏まえ、残る問題と指摘の重複を確認する。
5. 実装準備レビュー：詳細実装計画の範囲がないことを記録する。存在しない計画を補って合格扱いにはしない。

現稿は概要・問題・目標の草案である。完成した機能仕様や実装計画として足りない項目と、現稿に書かれた内容自体の矛盾を分けて報告する。

## レビュー担当の分離と限界

各担当は `fork_turns: "none"` で開始し、親の会話履歴を渡さない。指定した役割、対象文書、基準、許可された参考ファイルだけを読むよう依頼する。会話ログ、メモリー、以前のbriefや設計書を使った補完は禁止する。

ファイルシステムは共有され、ホストの指示ファイルまで完全に隔離されることは確認していない。レビュー担当は読み取り専用とし、ファイルの変更、ビルド、テスト実行は行わない。

レビュー報告は問題の指摘であり、設計の変更案や代替案をユーザーが採用したことを示さない。
