# 画像の保存と復元

添付写真、AIが返した画像、人物アイコンを対象に、端末内と今後のGit・ZIPバックアップで画像本体を暗号化する。動画・PDF・テキスト・会話・記憶・ファイル名はこの暗号化の対象外。写真を検索して長期記憶から見せ直す機能は、この変更には含めない。

## 使い方

1. 画像は通常どおり添付・生成・表示する。画像のある人物では「管理 → バックアップ → 画像の復元キーを書き出す」からキーを保管する。
2. 復元キーの保存が成功するまで、その人物の画像を含むGit差分・ZIP書き出しは停止する。会話と画像は端末に保持し、理由を表示する。キーを書き出した後、Git保存・ZIP書き出しを再実行する。
3. キーは画像バックアップとは別の安全な場所に保管する。キーは暗号化されていない復元用の秘密情報であり、画像バックアップと両方を取得した人は画像を復号できる。キーの保存先をアプリから保証することはできない。
4. 画像カードの「保存」は、ダウンロードへの通常画像の書き出し。このファイルは今回の暗号化の対象外になる。

端末の鍵も復元キーも失うと画像を復号できない。復元キーは画面、ログ、Git、ZIP、会話に自動で含めない。人物を削除すると端末内の鍵も削除する。

## 保存方式

- 人物ごとにSecureRandomで256ビットの画像用の鍵を生成する。鍵は既存のConnectionStoreを使い、Android Keystoreの鍵で暗号化し、アプリのnoBackupFilesDirに保存する。Application起動時に初期化し、画面がない処理でも同じ鍵を使用する。
- AES-256-GCM、毎回新しい96ビットのnonce、128ビットの認証タグを使う。人物IDと画像のファイル名を認証対象に加える。改ざん・別人物の鍵・別ファイルへの差し替えは復号時に失敗する。
- バイナリ形式はASCIIの`CIMG`、バージョンの1バイト`01`、nonceの12バイト、暗号文、タグの16バイト。合計33バイト増える。
- 端末内の既存のattachment参照とファイル名を保持し、中身だけを暗号化する。表示・AIへの送信・明示的な書き出し時にメモリ上で復号する。
- Gitでは`media/<既存のファイル名>.enc`と`icon.png.enc`、ZIPでは現在のsnapshot内の同名ファイルに暗号文を保存する。復元キーのファイルには`format=conversation-images-v1`、`person_id`、Base64の`key`を保存する。
- 暗号化済み画像に対応する鍵が見つからない場合、新しい鍵を黙って作って置き換えない。保存失敗時に平文へ切り替えない。

[Androidの暗号化ガイド](https://developer.android.com/privacy-and-security/cryptography)と[Java CipherのGCM仕様](https://docs.oracle.com/javase/8/docs/api/javax/crypto/Cipher.html)を参照。

## 既存データと制限

アプリ起動時、全人物のmedia内の写真・アイコンと、アプリ内部のexport内に残っている画像を移行する。元の写真を検証し、暗号化した一時ファイルの復号を確認してから原子的に置き換える。失敗は表示し、元データを消して進めない。個別画像の読み込み時も未移行画像を保護する。移行処理はフラッシュストレージから旧ブロックを安全消去する保証にはならない。

以前のGit履歴、他端末のコピー、既に書き出したZIPやダウンロード画像は変更しない。既存リポジトリの過去画像を安全な状態に戻すには別途履歴・コピーの扱いを検討する必要がある。過去のGit画像を自動で全件再送したり、履歴を書き換えたりはしない。

画像を会話に含めるとOpenAIに画像を送信する。生成時は指示文をOpenAIに送る。アプリ内の保存暗号化は送信先の処理・保持条件を変えない。画像の名前やハッシュ、会話に含めた写真の説明文は隠さない。OSの侵害や実行中アプリのメモリを読まれる攻撃を防ぐものではない。

## 元の端末なしで画像を復元する

Gitのコピーか展開したZIP、別に保管した復元キーファイル、Java 17以降とこのソースを用意する。バックアップの人物IDが復元キーファイルのperson_idと対応する必要がある。Conversationリポジトリのルートで次を実行する。

```powershell
java android/src/jp/tekewo/conversation/ImageVault.java "D:/Backup/Conversation-images.key" "D:/Backup/expanded-person" "D:/RecoveredImages"
```

出力先はまだ存在しない、入力フォルダの外の場所を指定する。入力は変更せず、フォルダ内をたどって認証に成功した`.enc`画像を通常画像として書き出す。既存の出力先には上書きしない。途中で不正な画像や鍵を検出すると停止し、それまでに復元した画像は出力先に残る。通常画像になるため、出力先も安全に管理する。

これは画像本体を取り出すための手段であり、会話・人物をアプリへ一括復元するUIではない。

## 検証

2026-11-15にDebugビルドとOdinの70テスト、`scripts/test-connection.ps1`を実行。暗号文の改ざん・別の人物やファイルへの差し替え・間違った鍵の拒否、Git/ZIPの暗号化、既存画像と中断したexportの移行、Javaソースを直接起動する別プロセスでの復元を確認した。

専用Android 16エミュレータで画像関連16テストが成功。添付・生成画像の表示と送信用画像データ、ダウンロード、人物アイコン、Keystoreで保護した鍵の再読込、復元キーの書き出し失敗時の停止、破損・紛失した鍵を置き換えないことを確認した。

v0.9.1の署名済みReleaseでは、ONNX JNI名の検査と`test-release-startup.ps1 -Serial emulator-5554`によるモデル推論・Activity起動試験が成功。`-ImageSecurity`の専用プローブでも、インストール済みRelease内の実装を使って写真・生成画像の暗号化、送信用画像データ、復元キーの書き出し前の停止、改ざん・鍵の破損・紛失の拒否、元の端末の鍵なしでの復元を確認した。v0.9.0からの上書き更新とUID保持も確認したが、旧版の試験環境は会話・人物がない状態だった。

エミュレータ内でモデル配布先の名前解決に失敗したため、サイズとSHA256が配布モデルの固定値に一致するモデルを試験用プローブで事前配置して推論した。初回モデルダウンロード、実OpenAI通信、実GitHubへの写真送信、物理端末は今回の確認に含めていない。
